# Working in this repo

Adapted from the rules in the rmtool-dev repository's CLAUDE.md. The
release/build/CI items specific to rmtool are not carried over.

- **About this file**: stays branch-agnostic -- repo-wide policy and
  conventions only, true on every branch, including ones that don't
  exist yet. If it's about a specific piece of in-progress work or a
  specific ticket, it belongs in `docs/dev/BRANCH_STATUS_<branch-name>.md`
  instead.
- Never commit straight to `main` or `develop`. Work on a named branch,
  merge it into `develop` with `--ff-only`, and merge `develop` into
  `main` (`--ff-only`) only after confirmation. A push to `main` that
  brings in `develop` renders the movie and replaces the file attached to
  the `movie-latest` release (`.github/workflows/publish-movie.yml`).
- Python runs only from the project virtualenv, kept outside the repo at
  `~/.venv/askap-polarimetry`: use `~/.venv/askap-polarimetry/bin/python`.
  Install every library inside it, never into system Python. Record
  versions in `requirements.txt`.
- Source data under `~/DATA/askap-pol/` is read-only
  input. Never write into it.

## Ticketing convention

- When starting work on a new branch, ask which milestone or report it
  is aimed at.
- Every branch gets its own `docs/dev/BRANCH_STATUS_<branch-name>.md`,
  named after the branch so merges never collide.
- That file is a minimal index: one line per task, with a status
  (Planning / WIP / Done) and a link to a separate detail doc for
  anything substantial. No narrative design detail in it.
- State the branch name inside the file's content too, so it is
  self-identifying out of context.

## Writing style -- applies to commits, docs, code comments, printed messages

- **No AI attribution, anywhere.** No `Co-Authored-By` trailers, no
  "generated by" mentions, in commit messages, code comments or
  documentation. Standing rule, no exceptions.
- **No intensifier/hyperbole words** -- `real`, `genuine`, `actual`,
  `true`, `truly`, `really`, `actually`, `very`, `extremely`,
  `completely`, `entirely`, `highly`, `significantly`, and the wider
  family -- in prose, comments, commit messages or printed messages.
  State facts plainly. Full word list, litmus test and the legitimate-use
  exceptions are in `docs/dev/INTENSIFIER_SANITIZATION.md`; read it
  before a sweep of more than a line or two.
- Comments explain WHY (a hidden constraint, a bug workaround, a
  non-obvious invariant), never WHAT, and never refer to "the current
  fix/task" (that belongs in the commit message).
- Docs: verify every claim against the current code before writing it,
  not from memory. Plain, direct tone.

## Before acting

- **Show the diff, get explicit confirmation, before every commit.**
  Never commit sight-unseen, even when told "commit" directly.
- **Verify code behaviour by reading the current source before
  asserting how it works.**
- **Sanity checks**: before relying on a number or a result, check it
  against an independent route (row counts against file counts,
  re-derive one value by hand, compare to a previous output). Say what
  was checked.
- Don't assert a quantitative or statistical claim (a rate, a
  baseline, an expected count) without computing it.
- **Confirm before any destructive command** (`rm -rf`, `git reset
  --hard`, force-push, deleting or overwriting anything not trivially
  recoverable), every time.
- **Present a design for confirmation before implementing** anything
  architectural or spanning multiple files.
- Never write to `/tmp` or other system temp paths. Use `scratch/`
  (gitignored except its README) and clean up once no longer needed.
- Run one thing at a time and wait for it; don't background or
  parallelize runs unless asked.
- Never let two different concepts share one generic variable or
  parameter name in the same scope.
- Domain rule: instrumental leakage (dLP) is measured at high Stokes I.
  Low Stokes I is noise-biased in fractional polarisation and must not
  drive a leakage estimate.
